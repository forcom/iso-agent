**A의 ERP 공통 틀, B의 업무 홈, C의 목록·원문·판단 구성을 유지한다. MVP의 업무 홈은 ISO 업무를 지원하는 조회·질의·초안 생성·지식 검토를 시작하는 화면이다.** 실제 업무 건의 생성·배정·결재·종결은 후속 단계로 구분한다.

업무 분장은 **저장소의 ISO 매뉴얼·절차서·지침서에 규정된 기능상 역할과 책임**을 기준으로 설명한다. Person에 연결된 역할과 온톨로지 권한으로 실행 가능한 기능을 결정하며 실제 조직도·부서 인원·페르소나의 성향으로 업무나 권한을 자동 생성하지 않는다. 정식 역할 지정·위임 승인과 건별 담당 배정은 후속 업무관리 기능이다.

이번 MVP의 완료 기준은 12.1의 이슈 성공 기준 5개와 12.3의 화면 수용 기준이다. 5절과 6.3의 후속 설계는 MVP 완료 조건에 포함하지 않는다.

[기존 이미지 시안 17종](../../../output/erp-ui-screens/2026-10-22/index.html)은 v0.2 확장형 ERP의 참고 자료다. 이미지별 적용 범위는 14절에 명시하며, MVP의 최신 배치는 4절·8절의 와이어프레임과 동작 명세를 따른다.

## 1. 확정한 화면 방향

### 1.1 시안과 상세 설계의 관계

A의 남색 상단 바·밝은 사이드바·파란색 주요 버튼으로 통일한다. B의 두 열 배치를 유지하되 MVP에서는 업무 도구와 지식 검토를 우선 배치한다. C의 지식 검토는 `fact.approve`에 따른 연결 검토이며 산출물 결재와 구분한다.

화면의 이름·본문·상태·수치는 저장된 자료와 조회 결과로 표시한다. 예시 업무 카드·가상 기한·완료율로 홈을 채우지 않는다. 매뉴얼은 `준수하여야 할 요구사항`, 양식은 `작성 구조`, 기록은 `수행 근거`로 설명한다.

### 1.2 MVP와 후속 단계의 경계

| 구분 | 범위 |
| --- | --- |
| MVP 포함 | 문서·양식·기록 조회, 시드 수동 가져오기와 지식 연결 검토, 기록 스캔·자동 fact 반영, 온톨로지 그래프·인용 탐색, 승인된 지식 기반 AIMS Q&A, Edu Score 영향 집합과 영향평가 초안, 위키 조회, Person 드롭다운·온톨로지 권한 |
| 후속 업무관리 | 역할 지정·위임의 승인 절차, 실제 업무 건의 생성·배정·기한·제출본·결재·이행 확인·종결, 초안과 업무 건의 저장 연결, 범용 양식 편집기 |
| 이번 MVP 제외 | 연간 계획 알림, 뉴스·법령·경쟁사 자동 수집·평가, Grok Bot, OAuth·비밀번호 실인증, F01~F04 자동 완성·records 확정 발행, 자동 ISO 적합성 판정 |

MVP는 Workers·Containers의 PyreWire·R2·D1 및 OpenAI API를 사용하는 이슈의 기술 방향을 유지한다. UI 변경만으로 프레임워크·호스팅을 바꾸지 않는다. 정기 업무 자동 생성·알림은 MVP 메뉴와 완료 조건에서 제외한다.

## 2. 업무 분장의 기준

### 2.1 요구사항에서 개인 업무 홈까지의 연결

~~~mermaid
flowchart LR
    M[매뉴얼 요구사항] --> P[절차서의 업무와 책임]
    P --> G[지침서의 수행 방법]
    P --> R[기능상 역할과 관련 자료]
    G --> R
    U[선택한 Person과 승인된 역할 연결] --> A[온톨로지 권한 판정]
    R --> H[MVP 업무 홈의 업무 도구와 근거]
    A --> H
    H --> Q[조회와 Q&A]
    H --> D[영향평가 초안]
    H --> K[지식 연결 검토와 자료 반영]
~~~

- **매뉴얼**은 준수 요구사항과 기본 책임·권한을 제공한다.
- **절차서**는 업무 개시 조건, 순서, 수행·검토·승인 책임과 산출물을 제공한다.
- **지침서**는 자료 수집, 작성, 근거 확인, 협업, 후속 확인 방법을 제공한다.
- **양식**은 작성 구조다. 빈 양식의 존재를 업무 수행이나 기록 완료로 계산하지 않는다.
- **기록**은 개별 업무의 실제 수행 내용·결정·근거다. 존재와 승인 상태를 별도로 확인한다.

위 구분은 [문서체계](../../manual/AIDU-AIM-01-01.md), [조직 및 역할절차서](../../procedure/AIDU-AIP-05-02.md), [활동관리지침서](../../guide/AIDU-AIG-08-01.md)에 따른다. 원문에 등장하는 부서명은 아래 기능상 역할과 연결되는 출처 표현으로 보존하고, 메뉴와 업무 배정의 고정 조직 구조로 사용하지 않는다.

### 2.3 업무 유형과 절차 연결

다음은 **규범 문서의 업무 유형 카탈로그**다. MVP에서는 담당 업무의 의미와 관련 절차·양식을 안내하는 데 사용하고, 업무 건의 시작·배정은 후속 단계에서 제공한다. 각 행은 진행 중인 업무 건이 아니다. `주관`만으로 승인권을 부여하지 않으며 검토·결정 경로는 개별 단계의 절차를 적용한다. 표의 양식은 연결 후보이며 조건부 양식은 적용 사유를 판단한 뒤 요구한다.

후속 업무관리에서는 시스템 수명주기 업무를 홈의 `도입·설계`, `데이터 처리`, `공급자·고객 책임`, `검증`, `배포·변경`, `운영·사건`, `불만·이의제기`, `종료` 시작 항목으로 나눈다. 각 항목에 AIP-08-01의 해당 4항과 AIG-08-02의 실무 항목을 연결한다. 법령 적용 여부 등 조건부 판단은 별도 근거 확인 상태로 유지한다.

### 2.4 후속 업무관리의 개인별 배정 규칙

이 절의 지정·위임·건별 배정은 후속 범위다. MVP의 문서 조회·Q&A·시드 가져오기에 이 승인 절차를 선행 조건으로 요구하지 않는다.

1. 업무 유형·단계에 필요한 기능상 역할을 규범 문서에서 정의한다.
2. 사용자의 역할 지정에 적용 범위, 효력 기간, 대리·위임 범위와 지정 근거를 연결한다. 기준 양식은 [역할·권한 지정서](../../forms/AIDU-AIP-05-02-F01.md)와 [업무분장 및 이해충돌 검토표](../../forms/AIDU-AIP-05-02-F02.md)다.
3. 업무 건을 개시할 때 대상 시스템·버전·개시 사유를 정하고, 해당 범위에 유효한 역할 보유자를 담당 후보로 제시한다.
4. 후보가 여러 명이면 배정권자가 담당자를 정한다. 역할만 있고 담당자가 없으면 `담당 미지정`으로 표시하고 공용 역할 대기함에 둔다. 이름순 첫 사용자를 자동 배정하지 않는다.
5. 검토자·승인자·독립 검증자는 수행자와 별도 필드로 지정한다. 자기 업무 내부심사와 독립 검증의 이해충돌을 확인한다.
6. 업무 분장과 시스템 접근권한은 별도다. 메뉴·자료 열람·수정 권한을 추가로 검사한다. 지식 연결 승인 권한은 기술 출시·문서 발행·리스크 수용 승인권을 뜻하지 않는다.
7. 사용자의 소속·직함·페르소나가 달라져도 역할 지정이 같으면 같은 업무 기준을 적용한다. 역할 변경 시 과거 결정자의 기록은 보존하고 미완료 건의 인계를 처리한다.

[페르소나](../../aidu-personas.md)는 화면에서 사용할 사용자 예시 자료다. P01~P15에 대한 업무·권한 자동 배정표는 만들지 않는다. MVP는 승인된 시드의 `holds_role`과 권한 정의를 사용한다. 이 연결은 정식 업무별 지정·위임·독립성 확인을 완료했다는 뜻은 아니다.

### 2.5 MVP의 역할과 실행 권한

기능상 역할은 담당 업무와 규범 근거의 설명에 사용한다. 메뉴·버튼의 실행 가능 여부는 선택한 Person에 대한 서버의 권한 판정으로 결정한다. 표시 역할명이나 직함만으로 권한을 주지 않으며 같은 권한의 기능을 겸임 역할 수만큼 중복 표시하지 않는다.

| MVP 동작 | 기존 실행 권한 | 화면 의미 |
| --- | --- | --- |
| 문서·양식 조회 | `doc.read` | 규범과 작성 구조 열람 |
| 기록 조회 | `record.read` | 작성된 기록 열람 |
| 요구사항·증거·변경 영향 조회와 Q&A | `query.ask` | 승인된 관계와 위키에 근거한 조회 |
| Edu Score 영향평가 초안 | `impact.draft` | 초안 생성, 공식 기록 발행 제외 |
| 규범 지식 승인·반려 | `fact.approve` | 개별 fact의 의미·방향·출처 검토 |
| 시드 검증·가져오기 | `seed.import` | 수동 지식 입력과 적용. 검토 완료 상태 반입은 8.5.1의 추가 조건 적용 |
| 문서·기록 스캔 | `record.scan` | 현재 배포된 자료의 목록·관계 반영 |
| 위키 조회 | `wiki.read` | 승인된 설명과 인용 열람 |

실제 역할별 권한은 [권한 정의](../../../packages/ontology/permissions.json)와 승인된 온톨로지에서 읽는다. 위 표는 기능과 권한의 대응이며 특정 사람에게 권한을 새로 배정하는 표가 아니다.

## 4. MVP 업무 홈 HOME-01

### 4.1 목적과 배치

홈은 선택한 Person이 ISO 업무에 필요한 정보를 찾고 도구를 실행하는 주 화면이다. B의 두 열 배치와 A의 공통 틀을 사용하며, 실제 업무 건·기한·결재 상태는 후속 단계에서 추가한다.

~~~text
┌──────────────────── 상단 바 / Person 선택 / 고정 홈 탭 ────────────────────┐
│ 왼쪽 메뉴 │ 업무 홈                         현재 역할과 실행 권한          │
│           ├──────────────────────────────┬────────────────────────────────┤
│           │ AIMS Q&A                     │ 지식 연결 검토                 │
│           │ 질문 입력 → 답변·인용 확인   │ 실제 검토 대기 연결 → 원문 확인 │
│           ├──────────────────────────────┼────────────────────────────────┤
│           │ 업무 도구                    │ 담당 역할과 규범 근거          │
│           │ 요구사항·증거 탐색           │ 역할명·근거 문서·허용 기능     │
│           │ Edu Score 영향평가 초안      │                                │
│           │ 시드 가져오기 / 기록 스캔    │                                │
│           ├──────────────────────────────┴────────────────────────────────┤
│           │ 최근 확인한 문서·기록·위키 / 매뉴얼·절차·지침·양식 바로가기    │
└──────────────────────────────────────────────────────────────────────────┘
~~~

왼쪽 약 2/3, 오른쪽 약 1/3을 사용한다. Q&A와 도구 실행이 가장 먼저 보인다. 도구는 단순 문서 링크와 구분하며 실행하면 입력·계산·결과 확인으로 이어진다. 허용되지 않은 기능을 가상 업무나 임의 수치로 대신 채우지 않는다.

### 4.2 AIMS Q&A와 업무 도구

| 항목 | 표시·동작 |
| --- | --- |
| AIMS Q&A | 질문을 입력하면 TRACE-01의 Q&A 모드로 이동하여 승인된 지식의 답변·출처를 확인. 요구사항을 미리 고를 필요 없음 |
| 요구사항·증거 탐색 | 요구사항 선택 → 관계 그래프 → 관계별 원문 인용. 미확인 증거를 별도 탐색 |
| Edu Score 영향평가 초안 | 변경 설명 입력 → 계산된 재검토 대상과 LLM 초안 확인. 업무 건 등록·담당 배정 불필요 |
| 시드 가져오기 | ADMIN-01의 시드 입력·검증 탭으로 이동. `seed.import`에 따라 제공 |
| 기록 스캔 | ADMIN-01의 스캔 대상·실행 화면으로 이동. 홈 클릭만으로 즉시 스캔하지 않음 |
| 자료 찾기 | 문서·기록·위키와 관련 절차·양식을 검색 |

도구의 노출과 실행은 2.5의 권한을 따른다. 절차상 담당 역할은 도구 옆 근거 설명에 사용하며, 역할명만으로 실행권을 가정하지 않는다. 여러 역할로 같은 도구를 사용할 수 있어도 한 번만 표시한다.

### 4.3 지식 검토 대기

`draft`이면서 `normative`인 관계 중 조회·검토가 허용된 항목을 표시한다. 목록에는 주체·관계·대상, 출처 문서, 확인 가능한 갱신 시각, `원문 확인`을 둔다. `auto_approved` 기록 관계는 대기 건수에 포함하지 않는다.

대기는 특정 개인에게 배정된 결재 건이 아니다. 제목은 `검토 가능한 지식 연결`로 표시하고, 개인 담당자·승인 마감일을 만들지 않는다. 건수는 권한 범위의 실제 조회 결과이며 실패는 `—`, 정상 빈 결과만 `0`이다. 승인·반려 후 홈과 검토함을 함께 갱신한다.

### 4.4 역할과 최근 자료

| 영역 | 내용 |
| --- | --- |
| 현재 역할과 근거 | Person의 승인된 역할 연결, 기능상 역할 설명, 확인 가능한 규범 출처. 지정 기간·위임은 저장된 근거가 있을 때만 표시 |
| 최근 확인한 자료 | 이 브라우저에서 직접 연 문서·기록·위키 최대 5개. ID·유형·열람 시각만 사용자별 로컬 저장 |
| 유형 바로가기 | 매뉴얼·절차서·지침서·양식·기록과 각 유형의 의미 |

최근 자료는 브라우저별 이력임을 안내한다. 접근권한이 사라진 자료의 제목·본문을 캐시에서 복원하지 않는다. `규범상 역할`, `시스템에서 허용된 기능`, `정식 역할 지정 승인`을 같은 상태로 표시하지 않는다.

### 4.5 초기·빈·오류 상태

| 상태 | 표시와 다음 행동 |
| --- | --- |
| Person 목록이 비어 있음 | 최초 예시 시드 준비 안내. 기존 bootstrap은 Person 0명일 때만 실행되는 데모 초기화로 구분하며 일반 시드 가져오기를 대체하지 않음 |
| 사용자 미선택 | `데모 사용자를 선택하세요`. 선택 전 개인별 자료·권한 조회와 변경 실행 없음 |
| 역할 연결 없음 | 역할 연결 미확인 안내. 서버가 허용한 기능만 제공하고 정식 역할 지정 결재를 새로 요구하지 않음 |
| 검토 권한 없음 | 검토 영역을 제외하고 허용된 조회·질의·도구 사용 |
| 검토 대기 없음 | `현재 검토 가능한 지식 연결이 없습니다` |
| 최근 자료 없음 | 자료를 열면 표시된다는 안내와 검색 |
| 일부 조회 실패 | 해당 영역만 오류·재시도. 실패를 0건으로 바꾸지 않음 |

## 5. 후속 업무관리와 수행 상세

이 절의 WORK-01·02·03은 후속 업무관리 설계다. MVP에는 실제 업무 생성·배정·기한·제출본·진행 상태를 요구하지 않으며, 아래 화면과 API는 MVP 메뉴·완료 기준에서 제외한다.

### 5.1 업무 목록 WORK-01

A형의 필터·표·하단 상세 구성을 사용한다. 기본 범위는 `내 업무`이고, 허용된 사용자에게 `역할 대기함`·`관리 범위`를 추가한다. 관리 범위는 유효한 위임·업무 범위로 제한하며 직함만으로 전체 공개하지 않는다.

필터는 업무 유형, 단계, 내 역할, 대상, 기한, 담당 여부다. 목록은 업무번호, 업무명, 대상, 현재 단계, 수행자, 검토·승인 역할, 기한, 최근 변경으로 구성한다. 행을 선택하면 요약을, 업무명 또는 `상세 열기`를 누르면 WORK-03을 연다. 기본 25행이며 50·100행 전환을 제공한다.

### 5.2 업무 개시 WORK-02

| 입력 | 규칙 |
| --- | --- |
| 업무 유형 | 규범 문서에 연결된 카탈로그에서 선택 |
| 업무 제목 | 유형·대상을 바탕으로 제안하되 사용자 확인 |
| 대상·범위 | 시스템·버전 또는 전사·특정 프로세스 등 해당 범위 필수 |
| 개시 사유 | 신규·변경·정기 검토·사건·불만·종료 등 해당 절차가 허용하는 사유 |
| 수행·검토·승인 역할 | 해당 유형·단계의 정의에서 제시. 임의의 일반 결재선으로 대체하지 않음 |
| 담당자 지정 | 유효한 역할·범위에서 선택. 미지정 건은 대기함으로 등록 |
| 기한·일정 | 확정한 값과 설정 근거. 조건부·정기 업무는 적용 조건과 기준일도 기록 |
| 관련 문서·양식 | 근거 조항·버전, 기본 양식, 조건부 양식의 적용 여부·이유 |

주관 역할이 전담자를 정하지 않은 상태에서도 업무 정의를 읽을 수 있다. 개인 수행에 필요한 배정이 없으면 `작성 시작` 대신 배정 안내를 표시한다. 정기 실행의 자동 생성·알림은 후속 범위이며, 최초 버전은 사용자가 개시 근거를 확인해 등록한다.

### 5.3 수행 상세 WORK-03

화면 위에는 업무명, 대상·버전, 현재 단계, 내 역할, 기한을 표시한다. 본문은 `개요`·`수행 및 근거`·`검토·결정`·`변경 이력`으로 나눈다.

- 개요에는 개시 사유, 역할별 담당자, 적용 절차와 양식을 표시한다.
- 수행 및 근거에는 단계별 해야 할 일, 연결 기록, 자료 부족, 미해결 사항과 다음 행동을 표시한다. 체크박스 선택만으로 수행 증거가 생성되지는 않는다.
- 최초 범위는 기존 산출물·기록 연결, 수행 메모, 근거 등록과 검토 요청이다. 모든 양식의 범용 편집기는 별도 범위로 둔다.
- 검토 요청에는 대상 버전, 요청할 결정, 핵심 근거, 미해결 사항·이견, 기한, 실행 제한 조건을 포함한다. [AIG-08-01 3.4](../../guide/AIDU-AIG-08-01.md)의 요청 정보와 연결한다.
- 변경 이력은 배정·제출·보완·결정·확인 이벤트를 시간순으로 표시한다. 이전 제출본의 결정과 새 제출본의 상태를 구분한다.

### 5.4 업무 상태와 완료 조건

아래는 화면에서 사용할 공통 상태 어휘다. 개별 업무 유형은 필요한 단계만 사용하며 단계와 전환 조건은 해당 절차에 연결한다.

| 상태 | 의미와 다음 행동 |
| --- | --- |
| 준비 | 업무가 등록되었으나 담당 지정·범위 확인 등이 남음 |
| 진행 | 수행자가 자료·산출물·근거를 작성·연결 중 |
| 검토 요청 | 지정 검토·승인 역할에 특정 제출본의 판단을 요청함 |
| 보완 요청 | 검토 결과의 보완 사항을 수행자가 처리해야 함 |
| 결정 완료 | 해당 단계의 판단이 기록됨. 실행·배포·효과성 확인 완료와는 구분 |
| 이행 확인 | 승인 조건·실행·조치 효과성 등을 지정 역할이 확인 중 |
| 완료 | 업무 유형별 종결 조건과 필요한 근거가 확인됨 |
| 보류 | 이유·보류 결정자·재개 조건이 기록된 업무 중단 |
| 취소 | 취소 결정과 사유가 기록됨. 업무 이력을 삭제하지 않음 |

```mermaid
stateDiagram-v2
    준비 --> 진행: 배정과 범위 확인
    진행 --> 검토요청: 제출본과 근거 확정
    검토요청 --> 보완요청: 보완 결정
    보완요청 --> 진행: 보완 수행
    검토요청 --> 결정완료: 해당 단계 결정
    결정완료 --> 이행확인: 실행 또는 후속 확인 필요
    이행확인 --> 완료: 종결 조건 확인
    결정완료 --> 완료: 후속 이행이 없는 유형의 종결 조건 확인
```

보류·취소는 해당 절차와 지정된 권한이 허용하는 단계에서만 가능하다. 보류 시 직전 단계와 재개 조건을 보존하고 재개 후 필요한 재검토를 판단한다. 반려된 제출본은 기록으로 남기며, 재제출이 허용되는 업무는 새 제출본으로 진행한다. 승인 버튼을 눌렀다는 이유로 모든 업무를 자동 완료하지 않는다.

## 6. 검토함과 C형 검토 상세

### 6.1 검토 대상의 구분

MVP의 REVIEW-01은 `지식 연결 검토` 목록만 제공한다. `업무 검토·승인` 탭과 REVIEW-02는 후속 단계에서 추가한다. 두 종류는 목록·원문·판단이라는 배치만 공유하고 승인 대상·권한·상태는 별도로 유지한다.

MVP 검토함의 기본 필터는 `normative`·`draft`다. 주체·관계·대상, 출처 문서, 상태, 확인 가능한 갱신 시각, `원문 확인`을 표시하고 출처·관계 종류·검토 상태로 좁힐 수 있게 한다. 목록 선택은 REVIEW-03을 열며 개인 배정자·업무 기한은 표시하지 않는다. 기록 자동 반영 건은 이 검토 목록에서 제외한다.

| 구분 | 후속 업무 검토·승인 REVIEW-02 | MVP 지식 연결 검토 REVIEW-03 |
| --- | --- | --- |
| 판단 대상 | 업무의 특정 제출본·산출물·요청 결정 | 원문에서 도출한 개별 지식 연결 |
| 기준 | 해당 절차의 역할·위임·검토 조건 | 연결의 의미·방향·원문 근거 |
| 권한 | 업무별 지정 역할·범위와 실행 권한 | `fact.approve` 및 해당 자료 접근권한 |
| 승인 결과 | 해당 업무 단계의 결정과 조건을 기록 | 규범 지식 연결을 `approved`로 변경 |
| 자동으로 뜻하지 않는 것 | 모든 후속 실행 완료, ISO 적합성 | 문서 발행 승인, 업무 수행, 운영 증거의 충분성 |

### 6.2 공통 배치

| 영역 | 후속 업무 검토 | MVP 지식 연결 검토 |
| --- | --- | --- |
| 왼쪽 대기 목록 | 내 역할에 요청된 업무, 대상·단계·기한 | 규범 지식의 검토 대기 연결, 원문·관계 |
| 가운데 주 영역 | 제출된 기록·산출물의 고정 버전, 근거 자료 | 연결의 출처 문서, 해당 인용 위치 |
| 오른쪽 판단 영역 | 요청 결정, 승인 근거 조항, 담당 역할, 조건·이견, 의견과 결정 | 주체·관계·대상, 출처·인용, 검토 의견과 승인·반려 |
| 보조 탭 | `제출본`, `근거 규정`, `관련 기록`, `이력` | `원문`, `연결 문서`, `출처`, `검토 이력` |

목록·본문·판단 영역은 독립 스크롤을 사용하고 판단 버튼은 오른쪽 하단에 유지한다. 다른 행으로 이동할 때 작성 중 의견을 잃지 않도록 한다. 기본 본문에는 검토 대상 자체를 표시하고, 근거 규정과 위키 설명은 별도 탭으로 연다.

### 6.3 후속 업무 검토 규칙

다음 규칙은 실제 업무 제출본을 관리하는 후속 단계에서 적용한다. MVP의 fact 검토에 업무 배정·위임 승인·종결 절차를 추가하지 않는다.

1. 요청 대상 버전, 수행자, 요청 결정, 지정된 검토·승인 역할을 먼저 표시한다.
2. 검토 의견과 결정 사유를 해당 제출본에 저장한다. 조건부 승인이 허용되는 단계는 조건·범위·확인 책임·기한을 구조화한다.
3. `보완 요청`, `승인`, `반려`, `보류` 중 업무 단계에서 허용하는 행동만 표시한다. 법적 금지나 수용 불가 리스크를 조건부 승인으로 면제하는 동작은 제공하지 않는다.
4. 검토 후 상위 승인자가 필요한 경우 검토 완료와 최종 승인을 구분한다. 같은 이름의 `승인` 버튼 하나로 여러 책임 단계를 생략하지 않는다.
5. 내부심사 배정과 독립 검증의 적격성·이해충돌 조건이 충족되지 않으면 해당 확정 동작을 제한하고 필요한 추가 검토·대체 역할을 안내한다.
6. 제출 이후 내용·담당 범위·권한이 바뀌면 최신 상태를 확인하게 한다. 이미 완료된 이전 제출본 결정을 수정해 덮어쓰지 않는다.

### 6.4 지식 연결 검토 규칙

| 저장 상태 | 화면 표시 | 허용 동작 |
| --- | --- | --- |
| `draft`, `normative` | 검토 대기 | 원문 확인, 의견 작성, 연결 승인, 반려 |
| `approved`, `normative` | 연결 승인됨 | 원문·검토 이력 조회 |
| `rejected`, `normative` | 반려됨 | 사유·원문 조회; 재추출·재제출은 별도 절차 |
| `auto_approved`, `record` | 기록 자동 반영 | 원 기록·관계 조회. 규범 지식 승인 대상으로 넣지 않음 |

`requires_record`는 `기록 양식을 요구함`, `addresses`는 `요구사항에 대응함`, `instance_of`는 `양식을 사용한 기록`, `evidence_for`는 `증거 후보 연결`로 표시한다. 방향과 원래 관계 코드는 상세 출처에서 확인할 수 있다.

현재 API에는 지식의 보류 상태가 없다. 첫 구현의 `나중에 검토`는 상태를 바꾸지 않고 목록으로 돌아가는 탐색 동작이다. 의견을 임시 보관했다면 그 상태를 명시한다. 지속되는 지식 보류 상태를 추가하려면 상태·사유·재개 규칙과 API를 별도로 설계한다.

### 6.5 원문과 인용의 표시

- 문서번호·제목·유형·확인 가능한 버전과 출처 위치를 함께 표시한다. ID의 `doc:`·`record:`·`tpl:` 접두사는 내부 식별과 표시용 번호를 분리해 처리한다.
- 인용은 실제 원문과 일치하는 범위만 강조한다. 줄 번호나 조항이 없으면 문구 검색 결과를 사용하되 여러 일치 위치를 임의로 하나로 확정하지 않는다.
- 저장된 인용·해시가 없는 경우 `인용 위치 미확인`·`추출 당시 원문 버전 미기록`으로 표시한다. 현재 파일 해시를 과거 버전의 검증값처럼 사용하지 않는다.
- 원문 미확보, 인용 불일치, 제출본 변경은 명시적으로 구분한다. 근거를 확인할 수 없는 지식 연결은 승인 동작을 제한한다.
- 요약은 `요약`으로 분리한다. 이미지의 축약 본문이나 생성된 설명을 원문으로 저장·표시하지 않는다.
- 원문의 상대 링크와 `#L행번호`는 앱 문서 뷰어에서 해석한다. 원본 Markdown 파일이 브라우저에서 줄 이동을 지원한다고 가정하지 않는다.

### 6.6 결정 저장과 충돌

저장 중 버튼을 잠그고 요청 완료 전 다음 건으로 자동 이동하지 않는다. 성공하면 지식 상세·검토 대기 목록·홈의 해당 상태와 건수를 함께 갱신하고, 처리한 건을 잠시 유지하면서 `다음 건`을 제공한다.

다른 사용자가 먼저 처리했거나 검토 대상이 바뀐 경우 `검토 대상이 변경되었습니다`와 최신본 비교·다시 확인 동작을 제공한다. 존재하지 않는 ID 또는 변경되지 않은 행에 대한 단순 성공 응답은 완료로 표시할 수 없다. 네트워크 오류에서는 작성 의견을 유지하고 저장 여부를 재조회한 뒤 재시도한다.

## 7. 문서대장과 기록대장

### 7.1 문서대장 DOC-01

A 시안의 목록·하단 상세 패턴을 적용한다. 유형 탭은 `전체`, `매뉴얼`, `절차서`, `지침서`, `양식`이고 기록은 별도 메뉴에 둔다.

| 요소 | 설계 |
| --- | --- |
| 검색 | 문서번호·제목, 유형. Enter 또는 `조회`로 실행, `초기화` 제공 |
| 목록 | 문서번호, 문서명, 유형, 연결 요구사항, `원문` |
| 선택 | 한 행 선택은 하단 상세, 문서명·상세 열기는 DOC-02. 선택 강조와 체크 선택을 혼용하지 않음 |
| 하단 상세 | `기본정보`, `연결 문서`, `원문`. 문서번호·유형·작성 역할·연결 절차·양식 |
| 내보내기 | 현재 필터 결과의 목록 CSV. 전체·선택 범위를 표시하고 본문 일괄 내보내기로 오해하지 않게 함 |
| 동기화 | `문서 목록 동기화`. 현재 배포된 자료를 재스캔하는 동작이며 파일 업로드·문서 개정 승인 기능이 아님 |

현재 문서 레지스트리의 `author`는 `작성 역할`로 표시한다. 이를 개별 업무의 현재 담당자로 사용하지 않는다. `updated_at`은 스캔 시 갱신되므로 `목록 반영 시각`으로 표시하며 `최종 개정일`·`시행일`로 부르지 않는다. 문서 발행 상태·시행 버전은 별도 데이터가 있을 때만 표시한다.

연결 요구사항은 승인된 관계에서 조회하고, 확인되지 않은 연결은 `연결 정보 없음`으로 표시한다. 조회 오류와 실제 빈 연결을 구분하며 문서 제목으로 조항 관계를 추정하지 않는다.

### 7.2 문서 상세 DOC-02

`원문`, `연결`, `출처` 탭을 둔다. 연결에는 요구사항·관련 매뉴얼·절차·지침·양식·기록을 유형별로 표시한다. 업무 건 연결은 후속 단계다. 원문 조회 권한과 연결 대상 조회 권한을 각각 적용한다. 작업 중 보조 문서를 열어도 원래 작업 탭과 질문·변경 설명·검토 의견을 유지한다.

### 7.3 기록대장 RECORD-01·02

기록번호, 제목, 사용 양식, 관련 절차·대상, 확인 가능한 기록 상태를 표시한다. 원 기록에 외부 업무번호가 있으면 출처 메타데이터로 보여 줄 수 있으나 앱의 업무 건으로 생성하거나 미구현 WORK-03으로 연결하지 않는다. 사용 양식·대상 연결·기록 상태가 없으면 `미확인`으로 남긴다. 빈 양식을 기록 건수에 포함하지 않는다.

상세는 `원 기록`, `관련 절차·양식`, `근거 연결`, `출처`로 구성한다. 스캔으로 생성된 `auto_approved` 관계는 `기록 자동 반영`이며, 기록 내용에 대한 사람의 검토·승인 여부는 별도 정보다. 기록 스캔 결과는 처리 기록 수와 생성·재반영 관계 수를 나누어 알린다. 8.5.2의 결과에서 기록 상세와 TRACE-01의 해당 Record로 이동하며 지식 승인 클릭을 요구하지 않는다.

## 8. 분석·위키·검색·관리 화면

### 8.1 요구사항 추적과 AIMS Q&A TRACE-01

#### 8.1.1 조회 모드와 배치

`요구사항 추적`, `증거 후보`, `미확인 증거`, `변경 영향`, `AIMS Q&A`를 같은 화면의 모드로 제공한다. 구조 조회는 요구사항·문서·시스템의 ID 또는 명칭으로 대상을 선택한다. Q&A는 요구사항을 선택하지 않은 상태에서도 질문할 수 있다.

~~~text
┌ 요구사항 추적·Q&A ─ 대상·조회 범위 ─ 조회 시각 ──────────────────────────┐
│ 요구사항 추적 / 증거 후보 / 미확인 증거 / 변경 영향 / AIMS Q&A          │
├────────────────────────────────────┬───────────────────────────────────┤
│ 관계 그래프                        │ 선택한 연결의 근거                │
│ 매뉴얼·절차·지침·양식·기록의 분기  │ 주체 → 관계 → 대상               │
│ 노드·관계 선택, 확대·전체 맞춤      │ 승인 구분·직접/계산된 연결        │
│                                    │ 출처·조항·실제 인용·원문 열기    │
├────────────────────────────────────┴───────────────────────────────────┤
│ 같은 결과의 관계 표 / 선택 경로 / 검색 범위에서 확인되지 않은 연결     │
└────────────────────────────────────────────────────────────────────────┘
~~~

관계 표는 그래프와 같은 결과를 표현하는 접근성 대안이며 그래프를 대체하는 원시 JSON 화면이 아니다. 그래프 노드 선택과 표 행 선택을 동기화하고, 큰 결과는 실제 총수·현재 표시 범위와 더 보기 상태를 알린다. 배치 예시의 모든 문서 유형을 채우기 위해 관계를 추정하지 않는다.

#### 8.1.2 노드와 관계의 의미

| 대상 | 표시·동작 |
| --- | --- |
| 노드 | ID·제목·종류. Requirement, 매뉴얼·절차·지침 Document, RecordTemplate, Record 등을 구분. 선택 시 메타·연결·원문 열기 |
| 직접 관계 | 주체·관계·대상과 실제 방향. 승인된 규범 fact와 자동 반영된 기록 fact의 상태를 각각 표시 |
| 계산된 경로 | 엔진이 반환한 규칙·구성 관계를 따라 표시. 직접 저장 관계처럼 바꾸지 않으며 경로의 개별 근거로 이동 |
| 관계 선택 | 오른쪽 패널과 관계 표에 같은 관계 ID·출처·인용을 표시. 선택한 연결과 무관한 claim의 출처로 빈칸을 채우지 않음 |
| 조회 맥락 | 조회 대상·목적·자료 범위·조회 시각. 실제 반환된 엔진·규칙·스냅샷 식별자는 근거 상세에서 확인 |
| 확인되지 않은 값 | 출처·인용·버전 미확인을 구분. 조회 실패를 빈 그래프로 표현하지 않음 |

그래프는 저장·계산된 연결의 방향과 분기를 보존한다. `요구사항 → 매뉴얼 → 절차 → 지침 → 양식 → 기록`이라는 고정 순서로 모든 자료를 강제 연결하지 않는다. `requires_record`, `instance_of`, `evidence_for`의 의미를 구분하고, 증거·담당·승인 관계를 일반 의존성처럼 무제한 전이하지 않는다.

#### 8.1.3 관계와 원문 인용의 연결

1. 관계를 선택하면 주체·관계·대상, fact ID, 지식 구분·상태, 출처 문서와 조항을 표시한다.
2. 실제 저장된 인용을 보여 주고 `원문에서 확인`으로 DOC-02 또는 RECORD-02의 해당 위치를 연다. 여러 일치 위치는 후보를 제시한다.
3. 계산된 경로에는 근거 관계 목록을 표시한다. 하나의 직접 인용이 없는 경로에 합성 인용문을 만들지 않는다.
4. 기록 메타데이터·파일 식별자에서 생성된 관계는 `추출 근거`로 표시한다. `form_id=...` 등 처리기가 만든 표현을 본문에서 그대로 인용한 문장처럼 강조하지 않는다.
5. 인용·해시·추출 당시 원문을 확보하지 못하면 해당 사실을 남긴다. 현재 파일의 해시를 과거 검증값으로 사용하지 않는다. 상세 확인은 6.5를 따른다.

스냅샷 ID가 있으면 해당 조회와의 연결을 표시한다. 고정 스냅샷을 사용하지 않은 조회는 `현재 승인 지식 기준`으로 표시하며 임의 ID를 붙이지 않는다. 과거 환경의 재현 실행은 이번 UI가 제공한다고 주장하지 않는다.

#### 8.1.4 증거 후보와 미확인 증거

증거 후보는 기록 ID·대상 요구사항·연결 경로·근거·확인 상태를 보여 준다. 미확인 증거는 해당 조회 범위에서 연결을 확인하지 못한 요구사항·기대 양식과 확인 가능한 기존 자료를 보여 준다. 확인된 연결이 없는 기록을 임의로 `evidence_for`에 추가하지 않는다.

`후보 없음`은 조회 범위에서 연결이 확인되지 않았다는 뜻이다. 기록의 부재·내용의 충분성·ISO 부적합을 동일하게 취급하지 않는다. 원문 확인, 범위 변경, 기록대장·스캔 결과로 이동할 수 있게 한다. 자동 적합성 점수·충족률을 만들지 않는다.

#### 8.1.5 AIMS Q&A

Q&A 모드는 질문 입력, 답변, 근거 목록을 넓게 배치한다. 근거 목록에서 문서·조항·실제 인용·관련 fact 또는 위키를 확인하고 원문·그래프로 이동한다. 홈에서 넘긴 질문은 동일한 입력으로 유지한다.

답변은 승인된 규범 지식·승인된 위키와 자동 반영된 기록 관계에 근거한다. 규범 설명, 기록에서 확인한 내용, 확인되지 않은 사항을 구분하며 생성 답변을 새 fact나 업무 결정으로 저장하지 않는다. 인용 목록에 있다는 이유만으로 답변의 모든 문장이 입증됐다고 표시하지 않는다.

답변 생성이 실패하면 질문을 보존하고 `답변 생성 실패`와 반환된 근거 결과를 분리해 보여 준다. 구조 조회 결과만 성공한 경우 답변 완료로 표시하지 않는다. 승인·스캔·시드 적용으로 자료가 바뀌면 이전 답변에 조회 시각을 남기고 다시 질문·조회할 수 있게 한다.

### 8.2 영향 집합과 영향평가 초안 IMPACT-01

#### 8.2.1 입력과 독립 실행

업무 홈 또는 분석 메뉴에서 실행한다. 필수 입력은 Edu Score 대상과 변경 설명이다. 지원 대상이 Edu Score임을 명시하며 실제 업무 건·담당자 지정·결재 요청을 선행 조건으로 두지 않는다. `연결 업무` 입력과 `업무 참고자료로 연결`은 후속 단계다.

화면 순서는 `변경 입력 → 계산·초안 생성 → 결과 확인`이다. 현재 API는 영향 집합과 초안을 한 요청에서 계산하므로 생성 전에 사용자의 근거 검토가 완료된 것처럼 단계 표시를 하지 않는다.

#### 8.2.2 두 결과 영역

~~~text
┌ 영향평가 초안 ─ 대상 Edu Score ─ 변경 설명 ─ [생성] ────────────────────┐
├───────────────────────────────────┬────────────────────────────────────┤
│ 재검토 대상과 근거                │ LLM이 생성한 초안                  │
│ 온톨로지 계산 결과                │ 변경 요약 / 검토 제안             │
│ 대상 ID·유형·제목                 │ 영향 시나리오 / 미확인 사항        │
│ 연결 관계·경로·규범·기록 근거     │ 근거를 참조하는 설명               │
│ 관련 양식·증거 후보               │ [복사] [Markdown 다운로드]        │
│ [그래프에서 확인] [원문 열기]      │ 초안 상태 표시                     │
└───────────────────────────────────┴────────────────────────────────────┘
~~~

| 결과 | 데이터와 의미 |
| --- | --- |
| 재검토 대상과 근거 | `impact_set`의 시스템·절차·활동 기준 결과, 관련 양식과 증거 후보를 대상 ID별로 정리. 중복 대상은 한 행으로 묶되 여러 도출 경로는 보존 |
| 연결 근거 | 관계 ID·방향·도출 경로와 출처. TRACE-01에서 같은 대상을 확인하고 원문으로 이동 |
| 생성된 초안 | `draft_markdown`의 변경 요약·재검토 설명·영향 시나리오·필요 양식·미확인 사항. LLM의 설명·제안임을 표시 |
| 추가 확인 제안 | 초안에 등장하지만 영향 집합에 없는 제안은 계산된 사실에 합치지 않음. 추가 확인 사항으로 구분 |

현재 계산은 시스템·관련 절차·활동의 연결을 중심으로 한다. 변경 설명의 의미를 정밀 분석해 실제 영향 범위를 확정했다고 표현하지 않는다. 화면에 원시 API 이름을 상시 노출할 필요는 없지만 계산 결과와 생성 설명의 출처는 분명해야 한다.

#### 8.2.3 성공·부분 실패·출력

| 상태 | 처리 |
| --- | --- |
| 영향 집합과 초안 성공 | 두 결과를 같은 요청·입력에 연결해 표시. 각 영역을 독립적으로 확인 가능 |
| 영향 집합 반환, 초안 실패 | 왼쪽 결과를 유지하고 오른쪽에 실패·재시도. 부분 성공을 전체 완료로 표시하지 않음 |
| 요청 전체 실패 | 입력 보존, 계산 결과 없음과 재시도 표시. 이전 결과가 있으면 이전 입력·조회 시각을 구분 |
| 입력 변경 또는 재생성 | 이전 요청의 응답이 새 입력의 결과를 덮지 않도록 관리. 현재 입력과 다른 결과는 이전 결과로 표시 |
| 복사·다운로드 | 초안임을 명시한 Markdown을 제공. 내용 확인용 출력이며 F01~F04 자동 완성·records 확정 발행·승인·업무 종결 없음 |

### 8.3 지식 위키 WIKI-01·02

목록에는 제목·상태·출처 요약을, 상세에는 설명·인용·원문 링크·관련 문서를 표시한다. 일반 탐색과 Q&A에는 승인된 위키를 사용하며 미검토 페이지는 허용된 검토 범위에서 구분한다. 위키 설명에서 원문·요구사항 그래프로 이동한다.

위키 페이지의 저장 상태와 개별 fact 승인 상태는 다르다. fact 하나를 승인했다고 위키 전체가 승인되거나 재생성되었다고 표시하지 않는다. MVP의 위키 입력·갱신은 검토한 `wiki_pages`의 수동 가져오기이며 별도 위키 승인 API가 이미 있다고 가정하지 않는다. 업무 건 링크와 `지식 승인 요청`이라는 새 결재 동작은 제공하지 않는다.

### 8.4 통합 검색 SEARCH-01

검색 대상은 접근 가능한 문서·양식·기록·위키·요구사항이다. 업무 건 검색은 후속 범위다. 결과는 제목·ID·유형·확인 가능한 상태와 원문 또는 그래프 진입을 제공한다. 없는 종류의 결과를 다른 자료로 대신 채우지 않는다.

현재 목록 API에서 문서·기록·위키를 검색할 수 있다. 요구사항 검색에는 권한이 적용된 개체 조회가 필요하다. 연결 전의 중간 화면은 실제 지원 범위를 명시하며, MVP의 요구사항 선택·추적 흐름은 제공해야 한다. 일부 조회 실패는 해당 범위가 빠졌다고 표시한다.

### 8.5 관리 설정 ADMIN-01

MVP 탭은 `시드 가져오기`, `문서·기록 스캔`, `지식 스냅샷`이다. 탭별 권한을 검사하고 최초 진입은 사용자가 실행할 수 있는 첫 탭으로 한다. 업무 기준 편집·정식 역할 지정 승인·대리·인계는 후속 탭이다.

#### 8.5.1 시드 입력부터 지식 검토까지

~~~text
┌ 시드 가져오기 ─────────────────────────────────────────────────────────┐
│ JSON 파일 선택 또는 붙여넣기 / 스키마·예시 시드 보기                    │
│ [검증만 실행]  [기존 fact 덮어쓰기: 해제]                               │
├────────────────────────────────────────────────────────────────────────┤
│ 검증 결과: 개체 / 규범 fact / 위키 / 건너뜀 / 오류                     │
│ 항목 ID·입력 위치 | 신규·변경·유지 | 반입 상태 | 오류·충돌              │
│ [입력 수정]                         [확인한 내용 적용]                 │
├────────────────────────────────────────────────────────────────────────┤
│ 적용 결과: 성공·부분 실패·실패 / 항목별 결과                           │
│ [가져온 검토 대기 연결] [위키 보기] [요구사항 추적]                     │
└────────────────────────────────────────────────────────────────────────┘
~~~

1. JSON 파일 읽기 또는 붙여넣기로 수동 입력한다. 파일 선택 자체는 서버 반입이 아니다. 스키마와 예시 시드 경로를 제공하고 잘못된 JSON은 입력 위치와 함께 표시한다.
2. 기본은 `검증만 실행`, fact 덮어쓰기는 해제다. 검증은 데이터를 바꾸지 않는다. ontology revision, 개체·관계 타입, 참조 대상, 상태, 필수 필드·출처의 유효성을 검증하고 항목 ID·입력 위치별 오류를 보여 준다.
3. 개체·fact·위키별 신규·변경·유지·건너뜀 예정 항목과 반입 상태를 확인한다. `가져오기`와 `연결 승인`을 구분한다. 신규 규범 fact는 `draft`가 기본이며 이미 검토한 `approved` fact·위키를 반입하려면 `seed.import`와 `fact.approve` 권한 및 검토 근거를 확인한다. 권한이 없으면 승인 상태 반입을 차단하고 상태를 명시적으로 수정해 재검증하도록 안내한다.
4. 오류가 없는 동일 입력·옵션에 대해 `확인한 내용 적용`을 실행한다. 입력·옵션·Person이 바뀌면 검증 결과를 무효화한다. 검증 후 기존 자료가 바뀐 경우 서버가 충돌을 반환하고 다시 검증하게 한다.
5. 적용 결과는 실제 성공·건너뜀·실패를 항목별로 보여 준다. 일부 적용됐으면 부분 실패로 표시한다. 타임아웃·재시도 시 이미 반영된 항목을 확인하며, 전체 원자 처리나 자동 복구가 구현되어 있다고 가정하지 않는다.
6. 반입된 draft fact 목록으로 이동해 C형 검토를 수행한다. 조회에 반영되는 시점은 승인 후다. 승인 상태로 반입한 자료와 위키는 별도 결과로 표시하며 자료 갱신 후 그래프·Q&A를 다시 조회한다.

현재 importer의 `overwrite`는 fact 중복 처리 옵션이며 개체·위키의 기존 ID는 별도로 갱신된다. UI에서 이를 모든 자료의 덮어쓰기 방지 옵션으로 설명하지 않는다. 종류별 변경 미리보기·검증 토큰·항목별 결과·승인 상태 반입 가드는 11.3의 MVP 보완 계약이며 현재 API에 모두 존재하지 않는다.

#### 8.5.2 문서·기록 스캔과 그래프 반영

스캔은 현재 배포된 `docs/`·`records/`와 corpus manifest를 읽는다. 브라우저가 사용자의 로컬 폴더를 직접 감시하거나 파일을 업로드하는 기능이 아니다. 새 기록은 배포 자료·manifest에 반영된 뒤 스캔 대상으로 제공되어야 한다. 이슈의 게이트 2도 이 준비 조건에서 검증한다.

~~~text
┌ 문서·기록 스캔 ─ 대상 자료의 반영 정보 ────────────────────────────────┐
│ [문서 목록 스캔] [기록 스캔]                                            │
├────────────────────────────────────────────────────────────────────────┤
│ 처리 기록 수 / 신규·갱신·변경 없음 / 반영 관계 수 / 실패 항목           │
│ 기록 ID | 처리 상태 | 관계 수 | 근거 정보 | 오류·실패 이유              │
│ [원 기록 열기] [이 기록의 그래프 보기] [실패 항목 확인·재시도]          │
└────────────────────────────────────────────────────────────────────────┘
~~~

| 단계 | 동작과 결과 |
| --- | --- |
| 실행 전 | 자료 구분·스캔 범위·접근 가능한 반영 정보를 표시. `record.scan` 검사 |
| 실행 중 | 중복 클릭 방지. 서버가 진척을 제공하지 않으면 임의 진행률을 만들지 않음 |
| 완료 | 스캔한 파일·Record 목록과 처리 결과, 생성·재반영된 관계 수를 표시. 전체 재스캔 수를 신규 기록 수로 표시하지 않음 |
| 자동 반영 | Record 개체와 `instance_of`·`produced_by`·`evidence_for` 등 실제 생성 관계를 표시. 기록 관계는 `auto_approved`이며 별도 승인 버튼 없음 |
| 그래프 확인 | 해당 Record를 선택한 TRACE-01과 원 기록으로 이동. 기록대장·조회 결과를 갱신하고 이전 Q&A 결과에는 재조회 안내 |
| 실패 | 파일·ID별 실패 이유와 재시도 제공. 일부 처리를 전체 성공으로 표시하지 않음 |

`자동 반영`은 내용의 정확성·충분성이나 정식 산출물 승인을 뜻하지 않는다. 원 기록의 검토 상태가 없으면 `미확인`으로 둔다. 문서 목록 스캔은 규범 fact를 자동 승인하지 않는다. 재스캔은 같은 Record·관계 ID를 중복 증식시키지 않으며, 사라진 파일의 과거 관계를 자동 삭제하는 동작은 별도 정책 없이 수행하지 않는다.

현재 기록 스캔 응답은 `scanned`, `factsCreated` 중심이다. 신규·갱신·변경 없음·실패 항목과 ID별 결과는 응답 보완이 필요하며, 없는 항목을 0 또는 성공으로 채우지 않는다.

#### 8.5.3 지식 스냅샷

`fact.approve` 권한이 있으면 `현재 승인 지식 스냅샷 생성`을 제공한다. 대상은 승인된 규범·자동 반영된 기록 관계이며 지식 승인이나 기록 내용 승인을 추가로 수행하지 않는다.

생성 후 서버가 반환한 ID·포함 fact 수와 확인 가능한 규칙·엔진 정보를 표시한다. 실제 바이트·버전이 고정되지 않은 저장물에 `감사 재현 완료`를 표시하지 않는다. 현재 API는 ID·fact 수를 반환하며 규칙·엔진 메타데이터의 실제 검증·조회 연계는 11.3의 보완 대상이다. 과거 스냅샷 재실행·비교 UI는 후속 범위다.

### 9.2 화면 폭별 동작

| 뷰포트 폭 | 공통·홈 | 검토 상세 |
| --- | --- | --- |
| 1440px 이상 | 220px 메뉴, 홈 두 열 | 대기 목록 240px, 본문 가변, 판단 320px, 사이 간격 16px |
| 1200~1439px | 메뉴 기본 접힘 72px, 홈 두 열 | 세 영역 유지, 본문 폭 우선 확보 |
| 900~1199px | 메뉴 접힘, 홈은 내용에 따라 한 열 | 대기 목록은 서랍, 본문·판단 두 영역 |

데스크톱 기준 검토 크기는 1440 × 900과 1920 × 1080이다. 작은 화면에서는 표가 영역 안에서 가로 스크롤될 수 있으며 페이지 전체가 가로로 밀리지 않게 한다. MVP 홈은 Q&A·도구·검토 순서로 쌓는다. 그래프와 인용은 목록·그래프·근거 전환으로, 영향평가는 입력·재검토 대상·초안 전환으로 제공하며 선택 대상을 유지한다. 후속 모바일 업무 목록은 제목·상태·다음 행동을 우선 표시한다.

### 9.3 접근성과 읽기

키보드만으로 메뉴·탭·필터·행·검토 버튼에 접근할 수 있어야 한다. 현재 위치와 포커스가 보이며, 다이얼로그가 닫히면 실행한 위치로 돌아간다. 상태와 오류는 색상 외 텍스트로 전달한다. 표 머리글과 입력 라벨을 연결하고 저장·로딩·오류 메시지를 보조기술에서도 확인할 수 있게 한다. 확대 시 핵심 동작과 본문이 겹치지 않는지 확인한다.

## 10. 공통 상태·권한·데이터 표시

### 10.1 화면 상태

| 상황 | 처리 |
| --- | --- |
| 최초 로딩 | 실제 구성과 같은 형태의 로딩 표시. 임시 0건·임시 승인 상태를 표시하지 않음 |
| 정상 빈 결과 | 데이터가 없거나 필터 결과가 없다는 설명과 적절한 다음 행동 |
| 필터 결과 없음 | 조건 표시, 조건 초기화. 전체 자료가 없다는 문구와 구분 |
| 조회 실패 | 실패 범위와 재시도. 기존 자료를 유지하면 `이전 조회 결과` 표시 |
| 저장 중 | 중복 제출 방지, 현재 요청의 진행 상태 표시 |
| 저장 실패 | 입력 유지, 실패 이유와 재시도. 저장됨 표시 금지 |
| 401 | 사용자 선택·세션 재확인. 이전 사용자의 민감한 내용은 숨김 |
| 403 | 접근 또는 동작 범위 부족. 다른 역할로 자동 우회하지 않음 |
| 404 | 대상 없음과 목록 복귀. 빈 원문 화면으로 대체하지 않음 |
| 409 | 변경 충돌. 최신 대상 확인과 의견 보존, 재검토 |
| 초안 생성 지연·실패 | 입력 보존, 생성 결과와 근거 조회 결과를 구분하여 표시 |

같은 화면에서 검색 조건·선택 대상이 빠르게 바뀌면 이전 응답이 새 선택 내용을 덮어쓰지 않도록 요청 순서를 관리한다. MVP에서 자료 적용·스캔·지식 승인 후에는 홈의 지식 검토, 관련 목록·상세·그래프를 갱신한다. 이전 답변·초안은 원래 입력과 조회 시각을 유지하며 자동으로 새 판단 결과처럼 덮어쓰지 않는다.

### 10.2 MVP 권한과 후속 업무 권한

| 구분 | MVP 적용 | 후속 업무관리 적용 |
| --- | --- | --- |
| 규범상 책임 | 업무 도구·근거 설명의 기준. 직함으로 실행권 자동 부여 없음 | 단계별 수행·검토·승인 역할과 예외 경로 |
| Person과 역할 | 승인된 `holds_role` 및 실제 온톨로지 권한. 정식 지정 결재를 선행 조건으로 요구하지 않음 | 적용 범위·효력 기간·대리·위임·이해충돌을 건별 배정과 함께 검사 |
| 실행·자료 접근 | 2.5의 권한과 자료 접근을 서버에서 검사. 원문·인용·그래프·내보내기에도 적용 | 업무 상태 전환 전용 권한을 추가하며 기존 지식 승인권으로 대체하지 않음 |

Person 선택은 비밀번호 없는 데모 세션이며 실제 신원 인증과 구분한다. UI는 서버가 반환한 역할·허용 동작으로 메뉴와 버튼을 표시하고 서버는 매 요청을 다시 검사한다. 권한 변경 시 오래된 화면의 실행도 거부한다.

검토·import 등 권한이 다른 최소 두 Person으로 허용·거부를 확인한다. 거부된 요청에서 데이터 변경이 없어야 하며, 직접 API 호출로 UI 제한을 우회할 수 없어야 한다. 시드로 역할·권한이 바뀌면 유효 권한과 홈을 다시 조회한다. 정식 역할 지정 승인 UI를 추가해야만 이 검증이 가능한 구조로 만들지 않는다.

### 10.3 화면에서 혼동하지 않아야 할 값

| 항목 | 구분 |
| --- | --- |
| 문서 역할 | 문서 작성 역할과 현재 업무 담당자 |
| 문서 시각 | 목록 반영 시각, 문서 개정일, 시행일 |
| 승인 | MVP의 지식 연결 승인과 기록 자동 반영; 후속 산출물 승인·역할 지정 승인·업무 종결 |
| 기록 | 빈 양식, 작성 중 초안, 수행 기록, 검토·결정 근거 |
| 증거 | 연결된 증거 후보와 충분성·적합성에 관한 사람의 판단 |
| 할 일 | MVP의 실행 가능한 도구·지식 검토 대상과 후속 단계의 실제 개시·배정된 업무 건 |
| 기한 | 절차의 주기·계기와 후속 업무의 건별 확정 기한. MVP 도구에 임의 기한 없음 |
| 출처 | 현재 조회한 원문, 추출 당시 원문, 승인 시 확인한 제출본 |

## 11. 데이터와 현재 구현의 연결

### 11.1 재사용할 API와 현재 한계

[현재 UI](../../../apps/worker/src/ui.ts)는 문서·기록·Fact·시드·질의·영향평가 초안·위키 탭을 제공한다. 업무 건·개인별 배정·업무 결재선은 현재 DB에 없으며 MVP UI의 선행 개발로 두지 않는다. 아래는 코드 확인 결과이며 배포 성공·MVP 게이트 통과를 뜻하지 않는다.

| 현재 데이터·API | MVP 활용 | 필요한 보완 |
| --- | --- | --- |
| `GET /api/persons`, `GET /api/me`, `POST /api/session` | Person 드롭다운·세션 | `/me`의 실제 역할·실행 권한·자료 범위 |
| `POST /api/bootstrap` | Person 0명일 때 배포된 예시 시드 초기화 | 일반 import와 구분. 이미 초기화된 환경에서 재실행해 덮어쓰지 않음 |
| `GET /api/documents`, `?type=record` | 문서·기록 대장 | 기록의 양식·상태 메타, 원문·관계 조회와 자료 접근 |
| `POST /api/corpus/scan-docs`, `/scan-records` | 목록 반영·기록 자동 fact화 | 항목 ID별 처리 결과·실패 이유. 현재 기록 응답은 scanned·factsCreated 중심 |
| `GET /api/facts?status=...` | 규범 지식 검토 목록 | 읽기 권한, 개체 이름·출처·인용·변경 토큰 |
| `POST /api/facts/:id/approve`, `/reject` | 개별 지식 연결 승인·반려 | 대상 상태·실제 변경 행·권한·버전 확인, 의견·결정 이력 |
| `POST /api/seed/import` | JSON 검증·적용 | 아래 11.2·11.3의 검증·변경·항목 결과·권한 가드 |
| `GET /api/wiki` | 승인된 설명·인용 조회 | 공개 상태·읽기 권한. 위키 승인·자동 재생성 API는 없음 |
| `POST /api/graph/query` | trace·evidence·missing·impact | 노드·관계·경로·원문 인용과 실제 엔진 정보를 화면용 결과로 정규화 |
| `POST /api/ask` | 답변과 graph·wiki·sources 인용 | 답변·근거·부분 실패를 구분하고 원문으로 이동 |
| `POST /api/impact/draft` | impact_set·draft_markdown | 두 결과 영역과 부분 실패 표시, ID·관계·출처 해석 |
| `POST /api/snapshots` | 승인 지식의 식별자 목록 저장 | 실제 규칙·엔진 메타와 조회 연결. 현재 응답은 ID·fact 수 |

### 11.2 현재 동작을 과장하지 않는 표시

- 시드 검증 결과의 `entities`·`facts`·`wiki`·`skipped`·`errors`를 신규/갱신/실패 항목 명세처럼 표시하지 않는다. importer는 항목별 처리와 부분 오류가 가능하며 전부 취소되는 트랜잭션을 보장한다고 설명하지 않는다.
- `overwrite=false`에서도 개체·위키는 기존 ID를 갱신할 수 있다. 종류별 적용 의미와 미리보기가 필요하다.
- 현재 문서 API의 사용자 미선택 처리와 Fact·위키의 읽기 검사가 일관되지 않다. 새 UI의 원문·인용·관계·위키 접근은 서버에서 함께 정리해야 한다. 메뉴 숨김만으로 완료하지 않는다.
- 원문 Assets 경로가 자료 접근 제한을 우회하지 않는지 확인한다. 다른 claim의 인용을 ID 대조 없이 재사용하지 않는다.
- 현재 승인 API의 단순 `ok`를 실제 변경의 증거로 사용하지 않는다. 존재하지 않는 ID, 이미 처리된 상태, 오래된 원문은 구분해서 처리한다.
- 그래프 질의는 설정에 따라 외부 Wirelog 또는 내부 엔진을 사용한다. Q&A와 영향평가는 현재 Worker 내부 엔진을 사용한다. 응답을 정규화하되 모두 Wirelog 계산으로 표시하지 않는다. 실제 Wirelog 연계 검증은 이슈 Phase 2의 별도 구현 조건이다.
- 현재 스냅샷 저장의 규칙·엔진 문자열만으로 실행 환경을 검증했다고 주장하지 않는다. 확인 가능한 메타만 표시하며 고정 원문·규칙 환경의 감사 재현은 별도 범위다.
- 문서·위키 목록은 클라이언트 필터·페이지 나눔으로 시작할 수 있다. 권한 범위와 결과 총수는 실제 조회 범위를 따른다.

### 11.3 MVP 화면을 위한 최소 응답 계약

아래는 신규·확장 설계다. 기존 API에서 이미 반환하는 값과 구분하여 구현한다. 업무 등록·배정·결재 API는 포함하지 않는다.

| 대상 | 화면에 필요한 계약 |
| --- | --- |
| `GET /api/me` 확장 | Person ID·표시명, 실제 역할 ID·이름, 허용 동작·자료 범위. 사용자 전환·권한 변경 후 재평가 |
| `GET /api/entities` 제안 | 개체 ID·이름·종류와 접근 범위. 요구사항 선택·그래프 노드 이름 해석·검색 |
| `GET /api/documents/:id/content` 제안 | 허용된 원문·문서 메타·조회 해시·저장 출처 상태. 등록된 경로만 조회 |
| 그래프 결과 정규화 | 노드와 종류, 주체·관계·대상·방향·fact ID, 직접/계산 구분, 경로별 근거 ID, 출처·인용 또는 미확인 이유, 조회 범위·시각·실제 엔진 정보 |
| 영향 집합 정규화 | 대상 ID별 도출 경로·관련 양식·증거 후보를 보존. 초안 본문과 독립된 결과로 반환·표시 |
| 지식 검토 | 대상 변경 토큰·확인 원문 정보·의견 수신. 검토 가능한 규범 draft만 갱신하고 결과·행위자·이력 반환. 403·404·409 구분 |
| 시드 검증·적용 | 입력·옵션·Person과 연결된 검증 토큰, 유형별 신규·변경·유지·건너뜀·충돌 목록, ID/JSON 위치별 오류, 예정 반입 상태, 적용 후 항목별 성공·실패·재조회 정보 |
| 승인 상태 반입 | `seed.import`만으로 `fact.approve`를 우회하지 않도록 서버 검사. 신규 승인 상태·승인된 대상의 덮어쓰기·승인 위키 반입에 필요한 권한·근거 검사. 최초 예시 시드 bootstrap은 별도 초기화 경로 |
| 스캔 결과 | 처리 파일·Record ID, 신규·갱신·변경 없음·실패, 생성·재반영 관계 수·ID, 추출 근거와 오류. 합계와 항목별 결과 일치 |
| 스냅샷 | ID·포함 fact 수와 실제 확인 가능한 메타. 사용한 조회에서만 snapshot ID를 연결 |

시드 검증 후 적용 시에는 서버가 동일 입력·옵션·사용자 권한·대상 자료의 변경 여부를 재검사한다. UI에서 버튼을 잠그는 것만으로 이 검사를 대신하지 않는다. 부재·미확인·빈 결과·오류를 서로 다른 결과로 유지한다.

### 11.4 후속 업무관리의 논리 모델과 API

이 절은 MVP 이후의 설계 참고다. 규범 역할·업무 카탈로그는 유지하되 아래 저장 모델을 구축해야 MVP 홈이 동작하는 의존 관계를 만들지 않는다.

| 개념 | 필요한 정보 |
| --- | --- |
| 기능상 역할 정의 | ID, 표시명, 책임 범위, 근거 문서·조항·기준 버전 |
| 업무 유형·단계 정의 | 개시 조건, 대상 종류, 단계별 수행·검토·승인 역할, 양식·근거, 전환·종결·예외 조건 |
| 사용자 역할 지정 | 사용자·역할, 범위, 효력 기간, 지정·승인 근거, 위임·대리 범위 |
| 업무 건 | ID, 업무 유형·정의 버전, 제목, 대상·버전, 개시 사유, 단계·상태, 기한, 역할별 실제 배정 |
| 제출본 | 업무 건, 제출 revision, 연결 기록·내용의 고정 식별자·해시, 요청 결정·근거·미해결 사항 |
| 검토·결정 이벤트 | 제출본, 행위자와 수행 역할, 결정·사유·조건, 시각, 확인한 근거 버전 |
| 업무 증거 연결 | 업무·단계, 양식, 실제 기록·버전, 근거 위치와 확인 상태 |

`WorkDefinition`과 `WorkItem`을 분리하여 규정에 업무가 있다는 이유만으로 모든 사용자의 진행 업무를 생성하지 않는다. 업무 기준·역할 지정·제출본·결정은 서로 다른 버전을 가진다. 규정 변경 또는 원문 삭제가 과거 결정의 근거를 소급해 바꾸어서는 안 된다.

후속 인터페이스는 `/api/work-definitions`, `/api/role-assignments`, `/api/work-items`, `/api/work-items/:id/submissions`, `/api/work-items/:id/decisions` 및 개인 업무 집계다. 경로는 제안이며 현재 API로 취급하지 않는다. 업무 실행 전용 권한·지정 범위·revision·이해충돌·종결 조건을 별도로 검사한다.

규범 문서 개정 시 후속 업무 정의를 `기준 재검토 필요`로 표시한다. 진행 중 업무의 결재선·양식을 조용히 덮어쓰지 않으며, LLM 연결 후보를 승인 없이 실제 배정 규칙으로 사용하지 않는다.

### 11.5 화면 구성 단위

MVP 구성 단위는 공통 틀·작업 탭·업무 홈·지식 검토 작업대·문서/기록 뷰어·그래프와 인용 패널·Q&A·영향 결과·시드/스캔 결과·공통 상태 처리다. 후속 업무 목록·수행 상세·제출본 결재는 독립해서 추가한다.

현재 단일 HTML 방식과 새 구성 방식의 선택은 구현 계획에서 정한다. 글자·버튼·표·그래프는 코드로 구현하며 시안 이미지를 화면 배경으로 사용하지 않는다.

## 12. MVP 범위와 수용 기준

### 12.1 이슈 성공 기준과 화면의 대응

MVP 완료는 [GitHub 이슈 #1](https://github.com/forcom/iso-agent/issues/1)의 다섯 성공 기준을 아래 흐름으로 확인한다. 시안 이미지의 존재나 후속 업무관리 기능 구현으로 이 검증을 대신하지 않는다.

### 12.2 필수 구현 범위와 후속 범위

필수 범위는 A형 공통 틀, B형 MVP 업무 홈, C형 지식 연결 검토, 문서·기록·위키 조회, 그래프·인용과 독립 Q&A, 영향 집합·초안의 분리, 시드·스캔·스냅샷 처리, Person 선택·온톨로지 권한이다. 11.3의 필요한 응답 보완도 화면 구현과 함께 처리한다.

후속 범위는 실제 역할 지정 승인·위임·개인 배정, 업무 목록·개시·수행·제출본·결재·이행 확인·종결이다. WORK-01·02·03과 REVIEW-02, 업무 결재 탭·업무 연결 저장·업무 검색은 이 단계에 속한다. 2절의 규범 역할·업무 유형은 후속 개발에서도 같은 근거를 사용한다.

정기 업무 생성·알림, 모든 양식의 편집기, 조직 간 서비스 운영, 실인증·전자서명, 범용 워크플로 편집기, 문서 발행·시행 버전 관리, 과거 스냅샷 재현·비교는 이번 MVP 완료 조건이 아니다. 이슈에서 제외한 자동 적합성 판정이나 자료 자동 수집을 후속 범위라는 이유로 승인된 기능처럼 취급하지 않는다.

### 12.4 후속 업무관리의 별도 확인 기준

후속 개발에서는 역할 지정·적용 범위·기간·대리·위임, 단계별 담당 배정, 특정 제출본의 검토·보완·반려·보류, 이해충돌·독립 검증, 실행·이행 확인과 종결을 검증한다. 같은 사용자의 겸임 업무 중복 집계와 임의 기한 생성도 방지한다. 이 기준은 G-01~G-05의 통과 여부에 합산하지 않는다.

설계서 단계에서는 이슈 범위·화면 흐름·데이터 의미·현재 API와 보완 계약의 일치를 확인한다. 구현 후에는 준비한 자료·Person으로 다섯 게이트를 실행하고 화면별 정상·빈·오류·권한 상태를 검증한다.
